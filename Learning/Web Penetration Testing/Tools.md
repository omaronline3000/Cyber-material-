# dig 

- `dig  <options> <domain> @<DNS namesever (optoinal) by default the one in your configs> <specified record (optional) by default is A>` 
    - the result is multiple sections with many info , if you wanna filter the result (like you wanna specific sectoin) use this format
        - `dig  +noall  +authority <domain> @<DNS namesever>` // display the authoritative server
        - `dig +noall +answer <domain> @<DNS namesever>` // display the specified record
        - `dig  +dnssec<domain> @<DNS namesever>` // using EDNS

- # Nmap

    - we use `nmap` to scan the open ports on specific target, and it will be in three status
        - open (the service is running and the port is open)
        - closed (port is exist , but the service is not running , so the port closed)
        - filtered (there is firewall deny the the port from specific IPs)
            - common popular firewalls on Linux is (iptables)
    - it display the ports, which i can not observe in my normal
    - by default it scan on the most famous 1000 port (often these ports use TCP)
    - nmap -hh
    - nmap -p 80,443 <domain/ip> → scans only these ports
    - nmap -p 1-70 <domain/ip> → scans IP range from 1 to 70
    - nmap —top-ports 2000 <domain/ip> → scans the most famous 2000 port
    - nmap -p 1-70 -sT <domain/ip> → scanning just for TCP
    - nmap -p 1-70 -sU <domain/ip> → scannnig for UDP
    - nmap -p 1-70 -sT -sU <domain/ip> → the requests here will doubled due to you scans on TCP and UDP
    - nmap -p 1-70  -A<domain/ip> → it strengths from the scanning (come with more details about the service which run on the port by sending many and various of payloads to test it and we use it if you do not know the service which run on this port wo it’s also send many payloads which manipulate with different protocols to discover the service “tcproute” if it could not identify the protocol or service)
    - nmap -p 1-70 -sn <domain/ip> → just pinging on the ip and display the hosts which reached
    - `nmap -p 1-70 -iL <file>` → read the host or multiple hosts from a file but should be separated by newline
    - also nmap not just for ports scanning
        - it is contain many and various scripts to do many tasks from brute-forcing through scanning and vulnerability assessments and to exploitation and malware detection
            - found on /usr/share/nmap/scripts
            - `nmap -p 1-70  —script=<name of the script> <domain/ip>` —> apply the script for this host on this port
    - `nmap -p 1-70 <domain/ip> —oG <filename>` → return the output on Grepable file
    - `nmap -p 1-70 <domain/ip> —oX <filename>` —> return the output on xml file
    - `nmap -p 1-70 <domain/ip> —oN <filename>` —> return the output on file
    - `nmap -p 1-70 <domain/ip> —oA <filename>` → return the output as all types of output and the gnmap one for GUI
    - nmap -p 1-70 -sS<domain/ip> → like sT , but it does not complete 3-handshek it jsut send the fits SYN packet and if there any response so the port is open
    - you may get a response from multiple IPs due to VIP

- # Burpsuit

	- there is three versions {community , professional , Enterprise}
		- Enterprise -> is a server version, not for manual testing, it just tracking and monitor and automatic testing (like Nessus) 
	- it used for web and mobile and API testing
    -  basically burp is just a proxy (server be in the middle between you and another server and it receive the response and foreword it to you and vice versa)
        - so burp use your local host (loopback) IP (127.0.0.1) as a proxy server , so the traffic will pass on the burp and burp foreword it to your browser
        - you configure that using browser extensions like “foxyproxy“ to add your local host as proxy on port 8080 (burp use your loopback and this port by default you can change it)
    - also it’s let you inspect the content of the HTTPS request which encrypted , and this happened by :
        - burp suite intercepts the traffic between you and the server as a proxy.
        - it’s act like your browser with the server and act like the server with your browser, so:
            - it receives the response from the server and decrypt it using public key in your device, then it let you inspect it
            - and foreword the response with fake certificate generated by burp suite (can not generate the real certificate because it already decrypted it (digital signature) )
            - so you should make your browser trust in burp suite certificate like (root CA)
    - because that the symmetric session key and handshake doubled
        - one created by the browser and used to connect with burp suite
        - and one created by burp suite and used to connect it with the server
        - and this two layer structure not observable, you does not fell any thing different
    - and it support WebSocket protocol

# crontab 

- use `cron` service `daemon` to schedule and automate tasks
	- **definition**:
		- every user in the UNIX-like operating systems has its own `cron` file 
		- the daemon repeatedly check the `cron` files , and that daemon who execute this scheduled scripts
		- after execution you got a mail inform you that the task is done, and you can send the output to specific file , or you can turn off the mail service 
		- system admins can manipulate with theses paths `/etc/crontab` or `etc/cron.d` , but normal individuals use `crontab -e command `  to modify their `cron` file

# OpenSSH

- that's is a implementation tool for SSH protocol 
- it's not one tool 
	- `ssh` -> start remote access session
	- `sshd` -> not tool , it's a `daemon` listen for coming SSH connections
	- `scp` -> transfer files over SSH instead of FTP
	- `sftd` -> interactive file transfer
	- `ssh-kegen` -> generate and manage `ssh` keys
	- `ssh-agent` & `ssh-add` -> manage private keys in the memory
	- `ssh-copy-id` -> Copy public keys to a remote host for passwordless login.
- used in
	- Remote Login & Administration
	- Port Forwarding / Tunneling
	- File Transfers
	- Key-based Authentication
	- Proxying & Jump Hosts
	- Securing Other Applications
