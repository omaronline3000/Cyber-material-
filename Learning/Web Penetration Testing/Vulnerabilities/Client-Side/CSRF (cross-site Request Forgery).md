

# Main Idea 

- It depends on specific scenario, when you be logged-in in specific website let we say it's bank called (bank.com) and you use another website in the same time in another tab in the same browser controlled by attacker
	- because you logged-in so your session ID saved in your cookies, and the cookies sent by default with every request sent from your browser to the website
	- so if the attacker added a script in the website that sent a request to the bank website which do anything malicious like changing passwords or withdraw all your balance, the request will sent and applied correctly (if the bank website infected to `CSRF` )
	- Although the attacker can not see response for his request due to the `SOP`, but Indeed, the request sent and applied on the server so he does not need the response
- That work with HTTP requests like [GET - POST]
	- and the others like [PUT - PATCH - DELETE], but with some requirements
- `CSRF Tokens` consider the standard way to protect against `CSRF` attacks
	- which is a random and unpredictable value generated by the back-end, sent to the client to use it when send any request for any sensitive action
		- can be sent via hidden parameter in `POST` request Form , or can be sent via special request header like `X-CSRF-TOKEN` or more .......
	- and because flawed validation of tokens, the attack maybe happened, like:
		- If there is a check on the `CSRF` token when it sent by POST request, otherwise like GET request it pass
		- it validate the request if it present, otherwise if it deleted from the request it does not validate
		- the token is not tied to user session, so it just validate if it issued by the server and kill it after that, so if the attacker logged in his own account and get a csrf key, then he can send a request for another account using it
		- the token is tied for a specific cookie, but not the session cookie, and this cookie and the `CSRF token` does not killed, so they are permanent but associated to each other if you will send with `CSRF token` so its associated cookie have to be included,so if you found a method to inject in the cookies victim like `CRLF injection` then you can attack the victim with any `CSRF key`
			- the cookie-setting function does not have to be in the same subdomain, it can be in another part of the app and when you inject the cookie in it, it leveraged all the requests or at least your potential `CSRF attack` subdomain
		- the token here tied to the cookie which carry the same value, that's mean the `csrf token` here is duplicated, and the validation is just checking if the sent parameter is the same as the cookie value, so you can just exploit it as the previous idea and it's easiest because you do not need the header value, you just need valid `CSRF token`
- Sometimes due to the `misconfiguration` of the Allowed HTTP requests type in the Back-end, I can send a request with another HTTP request which I should not do, like using GET request to exploit the default configuration `SameSite=Lax` to make an action just by clicking URL link
	- `Big Backet and Generic Routing`
		- many framework beside the functions which determine and wait the values of the parameters  from specific HTTP request which block the other types to sent this values except the determined one, it provide a function which accept the values overall, the HTTP method is not important, it just wait for the values
		- or it just do not determine a specific HTTP request to send the data it allow all types of the requests
	- `Method Override`
		- It's not a bug, actually it's a feature, because many clients `browser` maybe can not send requests like `PUT and DELTETE ...` it uses `_method`  parameter, so you use any request you want, and put in the `_method` value allowed method like `POST`
			- when the request arrive to the back-end, it first arrives to the `middleware` which intercept the request and observe the `_method` value so it change the request to this type and pass it t the controller `Back-End code` 
- another type of the validation is `Referrere-based`
	- the website does not use any type of `tokens` , it who is referred this request

	- it will send GET request to this URL and it will apply this process

# Testing Mindset

- Search for Request that makes an Action like Adding/altering/Delete Info or Send data or any action 
- Check If the Authentication done by the Cookies
	- If you found a `Authorizaiotn Header` which send an Authentication Token , try to delete it if the request achieved so the Authentication happened by cookies, otherwise 
- Check If there is `CSRF` Protection almost `CSRF TOKEN`
	- try to delete/edit/reuse the TOKEN
- check for weather the request is simple or complex
	- the `Preflight Request`normally cause blocking for the request, because the malicious website is not a valid to send according to `CORS` 
	- try to delete/edit/alter all components which make the request complex to see if you can convert it to simple request
- see if there is `SameSite` flag 
- see if there is validation on Referrer
	- try to delete it, and if it works add it in your exploitation
		- `<meta name="referrer" content="no-referrer">
		- or add this header in the request
			- `Referrer-Policy: no-referrer`
	- and sometime the developer use `lazy regex` which check if the referrer just contain my domain
		- so the attacker just need to rent a domain,and put the vulnerable as a subdomain in it
	- or sometimes it just check if the domain name string just mentioned in the Referrer, so you just need to put it in a fake parameter or put it as an Endpoint in your website
		- the problem, that the behavior of new browsers, which did not put the query parameters in the URL in the Referrer header
			- you simply enforce the browser to send this header
				- `Referrer-Policy: unsafe-url`
